2. PRODUCT GOAL AND PROBLEM STATEMENT
======================================================================

PRODUCT NAME: AttendWise AI
CATEGORY: Agentic AI-powered Time & Attendance Management and Exception Resolution

ONE-LINE PITCH:
AttendWise AI detects workforce attendance anomalies, investigates them using employee schedules and approved company policies, recommends evidence-backed resolutions, obtains human approval for consequential changes, and safely carries out authorized actions with a complete audit trail.

THE PROBLEM:
Organizations manage employees with different shifts, locations, work schedules, time zones, leave records, and attendance policies. HR and managers spend time reviewing exceptions such as:
- Missing clock-in or clock-out punches.
- Late arrivals and early departures.
- Overtime anomalies or potentially unapproved overtime.
- Conflicting or overlapping shifts.
- Attendance marked absent despite approved leave.
- Incomplete or inconsistent timecards.

A traditional system can record punches and flag anomalies, but the investigation and resolution often remain manual. AttendWise adds an AI-assisted investigation and resolution layer.

THE PRODUCT MUST NOT be represented as a replacement for a real Dayforce system or as a real payroll integration. It is a challenge prototype using synthetic data and clearly labelled simulated integrations. The product should demonstrate an architecture that could integrate with enterprise HR/time systems in a future phase.

CORE PRODUCT PRINCIPLES:
1. Detect with deterministic rules wherever possible.
2. Investigate with contextual evidence, not guesses.
3. Retrieve company policies using RAG and cite the exact source passages.
4. Let AI recommend; let authorized humans approve consequential changes.
5. Never silently modify a timecard or payroll-impacting value.
6. Persist workflow progress and recover from transient failures.
7. Make every important action observable and auditable.
8. Keep business records in PostgreSQL as the source of truth.
9. Use the AI service for reasoning and retrieval, not as the authority for permissions or final writes.
10. Be explicit about uncertainty, missing evidence, and conflicting policy sources.

5. CRITICAL ORCHESTRATION DECISION: INNGEST OWNS DURABLE BUSINESS WORKFLOWS
======================================================================

Use Inngest as the primary durable workflow orchestration engine.

WHY INNGEST:
- Attendance exception resolution can span minutes, hours or days.
- Some steps call LLMs or external services and may fail transiently.
- Manager/employee approvals require the workflow to pause without holding a server process open.
- A rejected decision, missing response or timeout must take a defined branch.
- Completed steps should not be repeated unnecessarily after a later failure.
- The team needs run traces to explain what happened during the demo.

IMPORTANT SEPARATION OF RESPONSIBILITIES:
- Inngest = outer business workflow orchestration, durable execution, retries, event waits, scheduled follow-up, concurrency controls, failure handling and resume logic.
- AI agents = bounded reasoning tasks called as discrete workflow steps (investigate, retrieve context, propose resolution, review output).
- Core API = source of truth and authority for domain writes, RBAC and approval decisions.
- PostgreSQL = source of truth for business data and case state.
- Qdrant = vector retrieval store.

DO NOT build two competing long-running orchestration systems. Do not put a multi-day human approval wait inside a Python process or an in-memory LangGraph run.

LANGGRAPH POLICY:
Default: do not add LangGraph to the MVP unless there is a concrete need for a cyclic reasoning graph that cannot be represented cleanly as a sequence of Inngest steps.
If LangGraph is used, keep it bounded inside one AI-service operation for a short reasoning subgraph. Inngest must still own the durable outer workflow, approval wait, retries and resume. Do not use LangGraph checkpointing as a second source of truth for long-running business process state. Document why it is present.

INNGEST IMPLEMENTATION REQUIREMENTS:
- Use the current official Inngest TypeScript SDK/API version compatible with the project.
- Verify syntax against official documentation before coding. Do not copy outdated v3 examples into a v4 project or vice versa.
- Use stable, descriptive function IDs and stable step IDs.
- Put every side effect (database mutation, HTTP request with external effect, notification send, file write, event send) in a durable step or in a safe idempotent command invoked from a durable step.
- Keep pure deterministic calculations outside side-effect steps where appropriate.
- Use step.waitForEvent for human/employee response waits. Use a unique correlation key and match tenantId, exceptionId, approvalId and workflow/run identity as appropriate.
- Use step.sleep / step.sleepUntil for scheduled delays rather than setTimeout or in-process timers.
- Use step.sendEvent for reliable downstream event emission from a workflow step.
- Use step.invoke only where useful to compose reusable durable functions; avoid unnecessary nested complexity.
- Configure concurrency/rate limits to protect the AI provider, Qdrant and downstream services.
- Support cancellation when an exception is resolved manually, withdrawn, superseded or no longer valid.
- Use Inngest failure handlers / onFailure or the current SDK equivalent to capture exhausted failures and persist a reviewable failure status.
- Use NonRetriableError (or current equivalent) for permanent business/validation errors that will not improve on retry.
- Retry only transient failures: network failures, provider 429/5xx, temporary database/network faults, etc.
- Never retry invalid input, missing required data, unauthorized approval, unsupported policy state or deterministic schema violations without a correction path.
- Use backoff/retry configuration supported by the installed SDK; make it configurable and document it.
- Store `inngestRunId`/function ID/thread ID references on the relevant workflow/case record where available, but never use a run ID as the only business identifier.
- Use stable idempotency keys for every business write and external notification. Inngest retries do not automatically guarantee exactly-once side effects.
- Protect against duplicate events and duplicate function runs using event IDs/function idempotency and database unique constraints.
- Make workflows safe when an event arrives twice or out of order.
- Make workflow event payloads versioned and validated.

7. ATTENDANCE DOMAIN RULES AND EXCEPTION TYPES
======================================================================

Create deterministic, testable rule functions. All thresholds should be configurable rather than hard-coded in scattered modules.

A. MISSING_CLOCK_OUT
Condition: a scheduled attendance record has a clock-in but no clock-out after the configured expected end time plus a configurable grace period or processing window.
Do not create an exception prematurely while the shift is still in progress.

B. MISSING_CLOCK_IN
Condition: a scheduled employee has no clock-in record after the configured grace period.
Avoid treating approved leave, holidays, rest days or schedule changes as absence.

C. LATE_ARRIVAL
Condition: actual clock-in is after scheduled start time plus configured grace period.
Store scheduled start, actual start, grace period and calculated lateness minutes.

D. EARLY_DEPARTURE
Condition: actual clock-out is earlier than scheduled end minus a configured permitted threshold.

E. OVERTIME_REVIEW
Condition: actual recorded hours exceed a configurable threshold or policy-derived threshold.
Do not conclude that overtime is approved or payable. Flag for policy/manager review.

F. SHIFT_CONFLICT
Condition: overlapping shifts or contradictory schedule assignments exist.

G. LEAVE_ATTENDANCE_MISMATCH
Condition: attendance is missing or marked absent while an approved leave record overlaps the scheduled shift.

TIME AND DATE CORRECTNESS:
- Store timestamps in UTC in the database.
- Store the employee/location IANA timezone for local display and schedule interpretation.
- Use timezone-aware date/time logic and daylight-saving-aware libraries.
- Support overnight shifts where a shift ends on the following calendar date.
- Do not calculate durations using naive local timestamps.
- Define breaks explicitly. Do not subtract unpaid breaks unless represented in the shift/attendance model or configured policy.
- Include boundary tests for exactly-at-shift-start, exactly-at-grace-limit, overnight shifts, daylight saving transitions where applicable, and missing punches.
- Do not infer a missing punch time from historical averages or AI model guesses. A proposed time must have a stated source/evidence and require approval.

EXCEPTION SEVERITY:
Use a simple configurable severity model (LOW, MEDIUM, HIGH) based on type and business rules. Do not use an LLM to determine severity where deterministic rules can do so.

EXCEPTION STATUS LIFECYCLE:
DETECTED -> INVESTIGATING -> WAITING_FOR_EMPLOYEE (optional) -> WAITING_FOR_APPROVAL -> APPROVED / REJECTED / NEEDS_MORE_INFO -> RESOLVED / ESCALATED / FAILED / CANCELLED.
Use a documented transition map and enforce it in backend/domain code. Do not allow arbitrary client-provided status changes.

8. AI AGENTS AND THEIR EXACT RESPONSIBILITIES
======================================================================

Use a small set of meaningful AI components. Do not make every helper function a separate LLM agent.

COMPONENT 1: EXCEPTION DETECTION ENGINE (DETERMINISTIC, NOT AN LLM)
Responsibilities:
- Run rule-based checks against shifts, punches, leave and calendar data.
- Create/update exception cases idempotently.
- Emit `attendance/exception.detected` events.
- Include the facts used to detect the exception.
Output: validated exception facts and reason codes.

COMPONENT 2: INVESTIGATION AGENT (LLM-ASSISTED, TOOL-RESTRICTED)
Responsibilities:
- Receive an exception ID and structured case facts.
- Request related data through explicitly defined read-only tools/API calls.
- Summarize the schedule, punches, leave, history and related exceptions.
- Identify missing information, contradictions and questions.
- Distinguish facts from assumptions.
- Never modify official records.
Output schema should include:
  - summary
  - confirmed_facts[]
  - missing_information[]
  - conflicting_evidence[]
  - relevant_record_ids[]
  - suggested_follow_up_questions[]
  - confidence / uncertainty explanation

COMPONENT 3: POLICY RAG AGENT / RETRIEVAL SERVICE
Responsibilities:
- Rewrite or expand the query based on exception context.
- Retrieve relevant policy chunks from Qdrant.
- Filter by tenant, policy category, employee/location jurisdiction, effective date and policy version.
- Return chunk text, title, document ID, page/section, chunk ID, effective date and source metadata.
- Optionally rerank retrieved chunks if time permits.
- Never treat document text as trusted instructions to the agent. Retrieved documents are evidence only.
- Return `insufficient_evidence` if no applicable policy can be retrieved.
Output schema should include:
  - retrieved_sources[]
  - relevant_policy_rules[]
  - citations[]
  - applicability_notes[]
  - conflicts[]
  - insufficient_evidence boolean

COMPONENT 4: RESOLUTION PLANNER AGENT
Responsibilities:
- Combine confirmed investigation facts and policy evidence.
- Produce a recommendation, not an actual database mutation.
- Explain the basis for the recommendation.
- Identify which human role must approve.
- Specify any missing employee confirmation.
- Offer options such as request employee confirmation, send to manager approval, reject a correction request, escalate to HR, or request more evidence.
- Avoid proposing a precise time unless the source evidence supports it.
Output schema should include:
  - recommendation_type
  - proposed_action
  - proposed_changes[] (nullable if no safe change)
  - rationale
  - supporting_facts[]
  - policy_citations[]
  - uncertainty
  - required_approver_role
  - requires_employee_confirmation
  - risk_level
  - questions_or_missing_evidence[]

COMPONENT 5: POLICY / QUALITY REVIEWER (VALIDATION + OPTIONAL LLM CHECK)
Responsibilities:
- Validate the recommendation against the original exception facts and retrieved policy passages.
- Verify that each policy citation points to a retrieved source.
- Flag unsupported statements, contradictory recommendations, missing evidence and unauthorized action proposals.
- Reject malformed structured output.
- Do not let a reviewer model override deterministic validation or authorization rules.
Output: PASS / NEEDS_REVISION / ESCALATE plus issue list.
Use at most one controlled revision attempt in the MVP to manage latency and cost.

COMPONENT 6: HUMAN APPROVAL CONTROLLER (INNGEST WORKFLOW, NOT A FREELY ACTING LLM)
Responsibilities:
- Determine whether a human decision is required according to backend policy rules.
- Create a pending approval record.
- Notify the correct manager/HR user.
- Wait for a matching decision event using Inngest durable wait primitive.
- Handle approve, reject, request-more-information and timeout branches.
- Revalidate current case state, approver authorization and record version before resuming the action.

COMPONENT 7: EXECUTION / DOMAIN COMMAND (DETERMINISTIC BACKEND SERVICE, NOT AN AUTONOMOUS AGENT)
Responsibilities:
- Apply a proposed correction only after valid authorization and a current version check.
- Use a database transaction and idempotency key.
- Save before/after snapshots.
- Update exception status.
- Add immutable audit event.
- Emit resolution event.
- Never trust a raw LLM instruction for SQL or direct execution.

COMPONENT 8: NOTIFICATION / FOLLOW-UP SERVICE (DETERMINISTIC)
Responsibilities:
- Create in-app notifications.
- Optionally send email via configured provider.
- Retry transient failures with Inngest.
- Deduplicate with stable notification keys.
- Escalate when configured deadlines expire.

LLM OUTPUT REQUIREMENTS:
- Use Pydantic models / JSON Schema for all AI outputs.
- Validate all outputs before they enter business workflows.
- Use structured output / tool calling where supported by the selected provider.
- Treat model output as untrusted input.
- Never execute generated SQL, shell commands, arbitrary code, or unrestricted API calls.
- Keep prompts versioned in source control.
- Log model/provider/model version, prompt version, latency, token usage where available, and a sanitized trace ID; do not log sensitive personal data unnecessarily.
- Implement bounded timeouts, bounded token budgets and a maximum number of reasoning/revision passes.

9. RAG / POLICY KNOWLEDGE DESIGN
======================================================================

The product needs a realistic policy knowledge base. Seed synthetic documents such as:
- Attendance and Timekeeping Policy.
- Missing Punch Correction Procedure.
- Grace Period and Late Arrival Policy.
- Overtime Authorization Policy.
- Shift Scheduling and Overnight Shift Guide.
- Leave and Holiday Calendar Policy.
- Manager Approval Matrix.

These must be clearly labeled synthetic demo policies, not real Dayforce policies or legal advice.

INGESTION FLOW:
1. Authorized HR admin uploads a PDF/DOCX/TXT file or uses seeded sample docs.
2. API validates file type, size and user permissions.
3. Store the original file in configured file storage.
4. Emit `knowledge/document.uploaded` event.
5. Inngest workflow starts ingestion.
6. AI service extracts text and structure.
7. Chunk by headings/paragraphs while preserving source page/section information.
8. Add metadata: tenantId, documentId, title, category, version, effectiveFrom, effectiveTo, location, department, page, section, chunkId, checksum.
9. Generate embeddings through a configurable embedding provider.
10. Upsert vectors to Qdrant using deterministic IDs so re-ingestion does not create duplicates.
11. Update PostgreSQL document/chunk ingestion status.
12. Mark document READY only after all required chunks are indexed; otherwise mark FAILED/PARTIAL and allow a safe retry.

RETRIEVAL FLOW:
1. Build query from exception type, employee location, shift facts and issue.
2. Apply metadata filtering before or during retrieval.
3. Retrieve top-K chunks.
4. Optionally rerank top candidates.
5. Check effective dates and conflicting policy versions.
6. Return citations with exact document/page/section/chunk identifiers.
7. Pass only relevant evidence to resolution agent.
8. If evidence is absent or conflicting, do not guess; request HR review.

RAG QUALITY:
- Include a small retrieval evaluation dataset with known questions and expected source documents.
- Measure Recall@K / Precision@K where practical and manually verify citations in the demo dataset.
- Ensure generated policy statements are supported by the cited chunk.
- Keep policy retrieval separate from attendance calculations.
- Use dense retrieval first; add hybrid search/reranking only after MVP works.

QDRANT COLLECTION DESIGN:
Use a documented collection name and vector dimension based on the configured embedding model. Store payload metadata for tenant, document ID, category, effective dates, location, policy version, page/section and chunk ID. Never hardcode a vector dimension that conflicts with the selected embedding model.

10. INNGEST EVENT CATALOG AND DURABLE WORKFLOWS
======================================================================

Create a typed event catalog (shared TypeScript types/Zod schemas or equivalent). Every event must have a stable name, version, correlation ID and validated payload. Include tenantId even if the demo has only one tenant, so the design does not accidentally mix organizations.

CORE EVENT NAMES (adapt names consistently, do not create duplicates with slightly different naming):
- `attendance/import.requested`
- `attendance/records.imported`
- `attendance/scan.requested`
- `attendance/exception.detected`
- `attendance/exception.investigation.requested`
- `attendance/employee-confirmation.requested`
- `attendance/employee-confirmation.submitted`
- `attendance/recommendation.created`
- `attendance/approval.requested`
- `attendance/approval.decision-submitted`
- `attendance/correction.approved`
- `attendance/correction.applied`
- `attendance/correction.rejected`
- `attendance/exception.resolved`
- `attendance/exception.escalated`
- `attendance/exception.cancelled`
- `attendance/workflow.failed`
- `knowledge/document.uploaded`
- `knowledge/document.indexed`
- `knowledge/document.indexing-failed`
- `notification/requested`
- `notification/sent`
- `notification/failed`

Use consistent naming style in actual implementation and document final names in docs/EVENT_CATALOG.md.

WORKFLOW A: ATTENDANCE IMPORT
Trigger: `attendance/import.requested`.
Steps:
1. Validate import metadata and permission.
2. Retrieve file from storage.
3. Parse and normalize rows.
4. Validate employee IDs, shift references, timestamps and timezone.
5. Reject or quarantine invalid rows with row-level reasons.
6. Upsert valid punches/records idempotently.
7. Persist import summary.
8. Emit `attendance/records.imported` and `attendance/scan.requested`.
Failure handling: retry transient storage/database issues; do not retry invalid file/schema errors; persist import failure details; allow admin retry after correction.

WORKFLOW B: EXCEPTION SCAN
Trigger: `attendance/scan.requested` or scheduled trigger.
Steps:
1. Fetch eligible shifts/attendance/leave records for a date range.
2. Run deterministic detection rules.
3. Upsert exception cases using a stable dedupe key such as tenant + employee + shift/date + exception type + record version.
4. Emit `attendance/exception.detected` per new/updated case.
5. Save scan summary and counts.
Controls: paginate/batch data, limit concurrency and avoid duplicate exception creation.

WORKFLOW C: INVESTIGATE AND RECOMMEND (PRIMARY DEMO WORKFLOW)
Trigger: `attendance/exception.detected` or manual re-investigation event.
Steps:
1. Load exception, employee, shift, punch, leave and prior case data from Core API.
2. Verify case is still open and not already resolved/cancelled.
3. Set status to INVESTIGATING using a guarded state transition.
4. Call Investigation Agent through AI service.
5. Validate investigation JSON output.
6. Call Policy RAG retrieval with case context.
7. Validate policy sources, effective dates and citations.
8. Call Resolution Planner with structured facts and evidence.
9. Validate recommendation with Pydantic/JSON Schema and deterministic rules.
10. Run Policy/Quality Reviewer.
11. If reviewer says NEEDS_REVISION, allow one bounded revision; if still invalid, set NEEDS_HUMAN_REVIEW and escalate.
12. Persist investigation result, evidence, citations and recommendation.
13. Decide required approval role using deterministic backend policy.
14. Emit `attendance/approval.requested` and continue into approval workflow, or route low-risk read-only outcomes as configured.
15. Emit workflow progress updates for UI.
Failures: transient LLM/network errors retry the failing step only; malformed outputs get bounded repair/retry then escalate; missing evidence escalates; permanent invalid case data is non-retriable.

WORKFLOW D: EMPLOYEE CONFIRMATION (OPTIONAL P1)
Trigger: request emitted by investigation/resolution workflow.
Steps:
1. Create confirmation request with expiry and unique correlation ID.
2. Notify employee.
3. Wait for matching `attendance/employee-confirmation.submitted` event with timeout.
4. If confirmed, persist response and resume investigation/resolution.
5. If disputed, attach employee statement and route to manager/HR.
6. If no answer by deadline, remind once (or a configured bounded number), then escalate.
Do not treat silence as confirmation.

WORKFLOW E: HUMAN APPROVAL (PRIMARY HITL)
Trigger: `attendance/approval.requested`.
Steps:
1. Validate recommendation is still pending and exception is still open.
2. Create approval record with unique approvalId, required role, assigned approver/manager, expiry, status PENDING and case version.
3. Create in-app notification and optionally email.
4. Set exception/workflow status WAITING_FOR_APPROVAL.
5. Wait with Inngest `step.waitForEvent` (or current official equivalent) for `attendance/approval.decision-submitted` matching approvalId + exceptionId + tenantId and appropriate correlation.
6. On timeout, mark approval EXPIRED, escalate to HR or manager's manager, notify relevant users and end safely or start a follow-up workflow.
7. On decision, validate the event signature/source through Core API, role, manager scope, current case version, approval expiry and allowed transition. Do not trust browser-provided role/tenant/approver identifiers.
8. APPROVE: call Core API command to apply proposed change using idempotency key and optimistic concurrency check.
9. REJECT: preserve original record, store reason, mark REJECTED or NEEDS_REVIEW and notify employee/HR according to policy.
10. REQUEST_MORE_INFO: create follow-up request, notify employee, and start/continue employee confirmation workflow. Resume investigation after response.
11. Record immutable audit event for every decision.
12. Emit correction/resolution events and notify stakeholders.
Human decision waits must not hold open an HTTP request or an in-memory worker. The workflow must survive deploy/restart.

WORKFLOW F: CORRECTION EXECUTION
Trigger: approved command/event, or invoked as a durable step from Workflow E.
Steps:
1. Re-fetch current record and validate version/eligibility.
2. Check approval record is valid and unused.
3. Calculate/apply allowed correction in a PostgreSQL transaction.
4. Use stable idempotency key e.g. `attendance-correction:{exceptionId}:{recommendationId}:{approvalId}`.
5. Save previous and new values, source evidence, approver, timestamp and reason.
6. Mark approval consumed and exception resolved in same transaction where possible.
7. Emit `attendance/correction.applied` and `attendance/exception.resolved`.
8. Notify employee/manager.
If record version changed between recommendation and approval, do not overwrite newer data. Mark STALE_REVIEW_REQUIRED and rerun/review.

WORKFLOW G: POLICY INGESTION
Trigger: `knowledge/document.uploaded`.
Steps: parse -> validate -> chunk -> embed -> upsert Qdrant -> save indexing metadata -> mark READY -> emit indexed event.
Make operations idempotent by document version/checksum/chunk ID. Keep old policy versions identifiable; do not silently overwrite historical documents used by prior decisions.

WORKFLOW H: REMINDERS AND ESCALATIONS
Trigger: approval or confirmation created; optionally scheduled scan.
- Wait until reminder interval using durable sleep.
- Check whether request is still pending.
- Send reminder idempotently.
- Wait for decision or next deadline.
- Escalate after configured deadline.
- Stop if case is resolved, cancelled or superseded.
Avoid infinite reminders. Make max reminder count configurable.

WORKFLOW I: ANALYTICS AGGREGATION (OPTIONAL)
Run on a schedule or after resolved events. Aggregate metrics from PostgreSQL. Do not ask an LLM to calculate KPIs. Store time-windowed aggregates only if necessary; for demo, simple indexed queries may be enough.

WORKFLOW J: GLOBAL FAILURE HANDLING
For every workflow:
- Capture function ID, run ID, event ID, tenant ID, case ID, step name and error category.
- Distinguish retryable transient errors from permanent business errors.
- After exhausted retries, persist a failed/review-needed state and emit a failure event.
- Provide an admin-visible failed workflow list or a documented Inngest dashboard route.
- Allow a safe manual retry/replay action after the underlying issue is fixed.
- Never retry a business write with a new idempotency key just to force it through.
- Never silently mark an item successful after an error.

======================================================================
11. RETRIES, FAILURE MANAGEMENT, IDEMPOTENCY AND CONCURRENCY
======================================================================

This is a critical engineering requirement. Build it deliberately, not as an afterthought.

ERROR CLASSIFICATION:
1. TRANSIENT:
- Network timeout.
- Temporary DNS/connectivity failure.
- LLM provider 429 rate limit or 5xx.
- Temporary Qdrant unavailability.
- Temporary database connection failure.
Action: retry with bounded backoff and appropriate retry count.

2. PERMANENT / NON-RETRIABLE:
- Invalid request schema.
- Unknown employee/shift ID after authoritative lookup.
- Unsupported exception type.
- User lacks approval permission.
- Approval is expired or already consumed.
- Policy not applicable and no safe alternative exists.
Action: mark appropriate state and route for correction/review; do not repeatedly retry.

3. NEEDS-HUMAN-REVIEW:
- Policy evidence is missing or contradictory.
- Employee disputes the recorded time.
- No reliable evidence supports a proposed correction.
- AI reviewer flags unsupported reasoning.
Action: stop automatic progression and ask a human.

4. STALE/CONFLICT:
- Attendance record changed after recommendation.
- Approval references an older case version.
- Two managers attempt conflicting decisions.
Action: use optimistic concurrency/transaction checks; reject stale command and require re-investigation.

IDEMPOTENCY:
- Give every event/business occurrence a stable identifier.
- Use unique DB constraints for deduplicated exception cases and approval decisions.
- Use stable command idempotency keys for corrections and notifications.
- Store processed command/event IDs where necessary.
- Make notification sends idempotent.
- Remember that durable workflow retries do not guarantee external side effects happened exactly once. A request may succeed externally but time out before the workflow records its result. The receiving service must deduplicate.

CONCURRENCY:
- Limit concurrent LLM calls.
- Limit concurrent policy ingestion/embed batches.
- Prevent multiple active correction workflows for the same attendance record where appropriate.
- Use tenant/case-level concurrency or database row locks/version checks where appropriate.
- Configure Inngest concurrency/rate-limit controls using the current SDK.
- Do not serialize all unrelated employee workflows unnecessarily.

TIMEOUTS:
- Set explicit HTTP timeouts between services.
- Set LLM connect/read/overall timeouts.
- Set approval deadlines and employee-confirmation deadlines.
- Use durable waits, not setTimeout.
- Define timeout behavior for every wait.

OBSERVABILITY:
- Structured JSON logs.
- Correlation ID across browser/API/Inngest/AI service.
- Trace IDs and case IDs.
- Inngest run traces.
- Metrics: workflow success/failure, retry counts, AI latency, retrieval duration, pending approval age, exception resolution time.
- Do not log full private employee documents or sensitive PII in prompts/logs by default.
